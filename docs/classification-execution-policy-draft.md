# 분류 실행 정책 합의 초안

권장안은 **정상 분류·정보 부족 보류·실행 실패를 분리하고, 고정한 조건으로 실행하며, 실패 기록을 보존하는 것**이다. 2026-10-18 세웅은 보류·실행 실패·재시도·자동 잘림 금지에 동의하고, 호출 전 거부 기록의 문서 보완과 기본 2048 유지를 제안했다. 아래에 그 검토와 보완 절차를 기록한다. 동료의 정책 동의는 PR 승인·병합이나 전체 팀 최종 확정과 구분한다. 2026-10-19 형언의 v2 결과 검토와 세웅의 문서 보완 재확인을 수신했다. 후속 로컬 실험 조건은 4096·600초·정규 18건과 경계 추가 6회이며 기본값 변경·실제 재실행·병합은 아직 완료하지 않았다.

## 합의할 항목과 권장안

| 항목 | 현재 동작·근거 | 권장 합의안 | 확정 상태 |
|---|---|---|---|
| 정상 출력 | type·rationale·needs_review 검증 | 세 유형 중 하나와 짧은 근거, needs_review=false | 기존 조건 유지·세웅 검토 수신 |
| 정보 부족·판단 보류 | type=null과 needs_review=true를 허용하는 실행 기록 존재 | 올바른 JSON이면 status=success로 저장하되 분류 보류로 별도 집계 | 기존 조건 유지·세웅 검토 수신 |
| 실행 실패 | prediction=null, 오류 status와 attempts 기록 | 네트워크·API·형식 오류·응답 잘림을 유형이나 정보 부족 보류로 변환하지 않음 | 기존 조건 유지·세웅 검토 수신 |
| 실패 후 진행 | 요청 결과가 실패하면 저장 후 중단·종료 코드 2. 호출 전 검증 거부는 결과 폴더·summary 없음 | 호출 단계 실패와 사전 검증 거부를 구분. 정상 보류는 다음 항목 진행 | 세웅 동의·문서 재확인 완료 |

| 긴 입력 | v1·v2 프롬프트 각각에 제목·본문을 더한 문자 한도 검사. 초과 시 호출 전 거부 | 자르지 않고 거부. 실행자가 아래 검증 기록 절차로 대상·사유·요청 0회 보존 | 잘림 금지 동의·문서 재확인 완료 |
| 로컬 생성 한도 | 기본 2048·timeout 300초 유지. 후속 실험은 명시적 4096·600초 | 정규 18건과 경계 추가 6회 실행 후 기본값 변경 판단 | 형언·세웅 실험 조건 동의·미실행 |
| 결과 저장 | 새 폴더만 허용, manifest·프롬프트·건별 결과·summary 보존 | 기존 결과 덮어쓰기 금지, 변경 조건·추가 시도를 별도 기록 | 기존 조건 유지·세웅 검토 수신 |

## 출력과 실패를 구분하는 예시

정상 분류:

```json
{"status":"success","prediction":{"type":"bug","rationale":"The configured policy does not take effect.","needs_review":false}}
```

모델이 본문 근거 부족으로 보류한 경우:

```json
{"status":"success","prediction":{"type":null,"rationale":"The report does not identify the failing behavior.","needs_review":true}}
```

생성 한도에 도달해 답변을 완성하지 못한 경우:

```json
{"status":"incomplete_response","prediction":null,"finish_reason":"length"}
```

위 예시는 계약 설명용이며 전체 결과 파일의 필드를 모두 표현하지 않는다. 세 번째의 prediction=null은 모델의 보류 답변이 아니다. HTTP 200만으로 성공으로 보지 않고 응답 완료·JSON 파싱·스키마 검증까지 확인한다. 로컬은 finish_reason=stop을 요구하며 제공자별 원본 상태도 남긴다.

## 재시도와 중단의 구체적인 의미

권장안은 기존 조건 유지다. Gemini는 일시적 429·5xx·시간 초과·네트워크 오류에 한해 최초 요청 후 최대 1회 추가 시도하고, 로컬은 자동 추가 요청을 하지 않는다. 인증 오류, 잘못된 JSON·스키마, 응답 잘림, 입력 초과에는 자동 재시도를 붙이지 않는다. 올바른 형식의 오분류도 재요청 사유로 삼지 않는다.

Gemini 기존 코드는 Retry-After와 지수 대기 중 큰 값을 적용하고, 30초를 넘는 대기가 필요하면 자동 반복하지 않고 결과를 반환한다. 실행기의 최소 시도 간격은 13초다. 이는 동결 실험의 호출 설정이며 현재 계정 한도나 서비스의 최신 이용 조건을 뜻하지 않는다. 크레딧·설정 문제는 원인을 해결한 뒤 새 실행으로 기록하고 반복 요청으로 해결하려 하지 않는다.

`run()`에서 받은 결과 레코드가 실패 상태이면 허용된 재시도 내역과 그 항목·summary를 저장하고 중단한다. 이 설명은 호출 전 검증 거부나 임의의 파일 저장 오류까지 summary 저장을 보장한다는 뜻이 아니다. 전체 항목별 대표 결과와 추가 진단·반복 결과를 분리하고 성공한 시도만 골라 원래 점수를 바꾸지 않는다. 현재 CLI에는 중단 지점 자동 재개 기능이 없으므로, 남은 항목 확인은 별도 절차·기록이 필요하다.

## 호출 전 검증 거부의 기록 — 2026-10-18 보완

현재 `main()`은 `load()`를 먼저 호출한다. 기존 v1 묶음 검증과 v2 길이 검사가 모두 통과해야 클라이언트·결과 폴더를 준비한다. 따라서 입력 길이 초과나 묶음 검증 실패는 stderr와 종료 코드 2만 반환하며, `run-manifest.json`·건별 결과·`summary.json`을 자동 생성하지 않는다. 이 단계의 모델 요청은 0회이며 전체 계획이 시작되지 않은 상태다. 실패 항목의 예측이나 dev 정확도를 만들지 않는다.

| 발생 단계 | 현재 자동 기록 | 이번 문서의 보존 절차 |
|---|---|---|
| 호출 전 묶음·길이 검증 거부 | stderr, 종료 코드 2. 모델 결과 폴더 없음 | 별도 검증 폴더에 stdout·stderr·종료 코드·묶음 식별자·대상 식별 근거·모델 요청 0회 기록 |
| 호출 후 실패 결과 반환 | 건별 결과·attempts·summary, 종료 코드 2 | 기존 결과 폴더를 보존. 정상 보류와 구분 |

다음은 **실행자가 남기는 기록 절차**이며 CLI의 새 자동 저장 기능이 아니다.

1. 실제 호출 전에 같은 묶음·제공자로 `--execute` 없는 오프라인 검증을 실행한다. 새 검증 전용 폴더에 명령 인자(인증정보 제외), 시각, 코드 커밋, 묶음 경로와 preflight 두 파일의 SHA-256, stdout·stderr와 종료 코드를 저장한다. 모델 결과 폴더와 구분하고 기존 기록은 덮어쓰지 않는다.
2. 거부되면 `validation-rejection.json`에 `stage=preflight`, `status=validation_rejected`, 실제 오류 메시지, `exit_code=2`, `model_requests=0`, `execution_started=false`를 기록하고 실제 호출을 진행하지 않는다. 이 필드는 사람이 작성하는 검증 기록의 제안이며 기존 summary 스키마가 아니다.
3. 현재 길이 오류 문자열에는 item ID가 없으므로 원문을 바꾸지 않고 추가로 대상을 확인한다. dev/reserve JSONL 각 행의 `item_id`와 `input.title`·`input.body`를 읽고, CLI와 같은 Python `len()`으로 v1·v2 프롬프트 각각의 길이를 더해 preflight의 `settings.max_input_chars`와 비교한다. 초과한 항목 ID, 어떤 프롬프트 기준인지, 합계 문자 수·한도를 `rejected_items`에 남긴다. 본문 자체나 정답·인증정보는 기록하지 않는다. 이는 원인 확인이며 해시 검증을 대체하지 않는다.
4. 파일 누락·파싱 실패 등으로 항목을 식별할 수 없다면 `rejected_items=null`, `item_identification=unavailable`로 기록하고 오류 파일·묶음 범위와 식별 불가 이유를 남긴다. 항목이 없었다는 의미의 빈 배열이나 추측한 ID를 쓰지 않는다. 원인 해결 뒤에는 새 검증 기록을 만들고 재검증한다. 고정 입력·manifest를 몰래 변경하거나 입력을 자르지 않는다.

다음은 **형식 설명용 가상 기록**이다. 실제 실험의 거부 기록이 아니다. 묶음 해시·명령·시각·코드 버전은 같은 폴더의 검증 메타데이터에 함께 남긴다.

```json
{
  "stage": "preflight",
  "status": "validation_rejected",
  "execution_started": false,
  "model_requests": 0,
  "exit_code": 2,
  "reason": "v2 input too long; truncation is forbidden",
  "item_identification": "manual_length_check",
  "rejected_items": [
    {"item_id": "microsoft/vscode#1", "prompt": "v2", "total_chars": 12001, "max_input_chars": 12000}
  ]
}
```

모델 서버가 토큰 컨텍스트 초과로 요청을 거절한 경우는 이미 요청을 보낸 호출 단계의 실패다. 이를 호출 전 문자 한도 거부나 요청 0회로 기록하지 않는다. 사전 거부의 자동 구조화 저장은 이번 문서 보완에 포함하지 않으며, 필요하면 별도 코드 변경으로 검토한다.

## 입력 길이와 생성 한도

12,000자는 실행기의 문자 한도이며 LM Studio Context 8192토큰과 단위가 다르다. 문자 검사 통과가 토큰 컨텍스트 적합성을 보장하지 않는다. 서버의 컨텍스트와 요청의 입력·생성 예산을 함께 확인하고, 초과 시 본문을 임의로 자르거나 정보 부족 보류로 바꾸지 않는다. 필요한 경우 입력 제한 방식부터 별도 합의한다.

로컬 Context 8192·GPU Offload 15·Q4_K_M·Thinking 켜짐/Unrestricted는 기존 실험의 확인된 설정 기록을 따른다. 향후 설정이 달라지면 해당 실행 manifest와 환경 기록에 변경값·확인 방법을 남긴다. 생성 한도와 컨텍스트를 혼동하지 않는다.

4096 후보의 근거는 실패 3건이 이번 별도 확인에서 모두 완료됐다는 점이다. 그중 한 건은 생성 2673토큰으로 2048을 넘었고 대부분 추론 토큰이었다. 나머지 두 건의 이번 응답은 2048 미만이어서 항목별 필요량이 고정됐다고 단정할 수 없다. 결과는 2정답·1오분류이며 4096이 모든 잘림을 해결하거나 정확도를 보장한다는 근거는 아니다.

4096을 채택한다면 새 설정 버전·적용 시작 시점을 정한다. 성능 수치를 제시할 때는 같은 조건의 전체 dev 실행이 필요하고, 실패 3건만의 추가 확인을 새 15건 점수로 표시하지 않는다. 후속 4096 실험은 형언·세웅이 동의한 별도 조건이다. Gemini는 기존 출력 한도 1024·timeout 45초를 유지하고 이번에 다시 실행하지 않는다. 로컬 CLI 기본은 timeout 300초이며 후속 명령에서만 600초를 지정한다. 생성 한도와 timeout 두 변경을 함께 기록하며 한도만 달라진 실험이라고 보고하지 않는다.

## 점수와 재현 기록

- 공식 dev 분모 15를 유지하고, 정상 보류·실패·미실행을 각각 함께 보고한다. 예비 3건과 Gemini 별도 반복은 dev 정확도에서 제외한다.
- 현재 기록: Gemini v2 14정답·1오분류, 로컬 2048 최초 dev 응답 12정답·3실패. 로컬 4096은 실패 3건만 2정답·1오분류로 별도 보고한다.
- 입력은 title/body만 사용하고 정답·원본 라벨은 모델에 전달하지 않는다. 데이터·프롬프트 해시, 모델 ID·설정, 시각·사용량·지연시간과 실제 시도 수를 남긴다.
- 로컬 후속 확인 ZIP은 final-summary.json을 기준으로 읽고 초기 summary 스냅샷과 구분한다. 결과 원문에 인증정보를 기록하지 않는다.
- v2 이후 기존 dev 오류를 맞추기 위한 추가 프롬프트 튜닝을 중단한다. 최종 평가는 기존 dev·예비 및 원본 30건과 겹치지 않는 별도 eval로 진행한다.

## 검토 완료와 후속 실험 — 2026-10-19

형언은 기존 결과·입력 해시·최초 응답 보존을 재검토하고 수치가 일치한다고 보고했다.
세웅은 커밋 `1ce0f84`의 호출 전 거부 기록 설명이 요청을 충족한다고 재확인했고 기존 실행 정책 동의를 유지했다.
이는 동료의 검토 범위이며 GitHub의 정식 Approve·PR 병합과 구분한다.

후속 로컬 실험은 **max_tokens=4096, timeout=600초**다. 정규 dev 15+예비 3 뒤
`#331658`·`#338087`을 각각 추가 3회로 총 24회 계획한다. v2·정답·모델·나머지 조건은 유지한다.
예비·반복은 dev 점수에서 제외하고 이전 2048 12/15·잘림 3건과 새 결과를 합치지 않는다.
4096에서도 잘리면 실패로 기록하고 한도를 계속 올리지 않는다.

로컬 반복 지원은 `4c9eac6`부터 포함된다. `--boundary-repeats`는 두 제공자 모두 0..3을
허용하며 기본은 Gemini 3·로컬 0이다. CLI 기본 생성 한도 2048·timeout 300초는 그대로다.
첫 실패 저장 후 중단 정책과 원래 정규/예비/stability 분리 구조를 사용한다.
정확한 코드·묶음·실행 명령·결과 확인은 [데스크탑 실행 안내](local-v2-4096-desktop.md)를 따른다.

현재 입력 토큰과 4096 생성 예산이 context 8192 안에 들어가는지 실행 PC에서 확인한다.
